## 1. 결론

사용자가 직접 확인한 현상이 맞다. 2026-08-24 14:14~14:19 KST의 로컬 자체 챗봇은
KB에 정답이 있는 질문에도 모두 “잘 모르겠다”는 취지로 응답했다. 같은 질문에 채널톡은
신청 시점, 신청 방법, 링크, 전화번호까지 정상 안내했다.

당시 실패의 직접 원인은 검색기가 정답을 못 찾은 것이 아니라 **애플리케이션의 일일 AI
호출 한도 500회가 자동 QA·실대화 재생으로 먼저 소진된 것**이다. API는 LLM을 호출하기 전에
`daily_limit`으로 종료했다. 그런데 당시 코드는 다음 세 경우를 같은 문구로 표시했다.

- KB에 실제로 답이 없는 경우
- 모델이 답변을 거절한 경우
- 일일 한도 소진 또는 모델 장애로 AI를 호출하지 못한 경우

그래서 이용자에게는 “정답을 모른다”로만 보였고, 개발자에게도 실제 장애 원인이 즉시 드러나지 않았다.

다만 일일 한도만 늘리면 문제가 끝나는 것도 아니다. 현재 구조는 임베딩·벡터 검색·의미 기반
Top-K·재순위화가 없는 **문자 휴리스틱 + KB 전문 LLM 입력 방식**이다. 자연어 표현이 예상질문과
조금만 달라져도 KB 직답 점수는 매우 낮고, 정상 질문 대부분이 LLM 가용성에 의존한다. 현재 QA
결과 80건도 55건이 AI, 4건이 FAQ, 1건만 KB 직답이었다. AI 예산이나 모델이 막히면 의도한 질문의
대부분이 다시 fallback으로 내려간다.

기존의 “완벽” 또는 “채널톡보다 우수” 판정은 신뢰할 수 없다. 채널톡 이력을 `closed` 상태 15건만
수집하고 이를 “전체 이력”이라고 잘못 표시했으며, 수정에 사용한 같은 질문으로 다시 평가했고,
채점기는 전체 답변의 의미 정확성보다 라우팅 종류와 기대 문서 인용 여부를 주로 확인했다. 최신
사용자 QA 대화가 속한 `initial` 상태 13건은 비교 데이터에서 빠져 있었다.

### 채널톡 대체용 현재 구성

```text
브라우저 ChatWidget
  └─ POST /api/chatbot/ask (클라이언트 제한 15초)
       ├─ 검토대기·정책 차단
       ├─ FAQ 문자 휴리스틱 매칭
       ├─ KB 문자 2-gram/부분포함 점수
       │    └─ qScore >= 0.66이면 KB 원문 직답
       └─ 나머지
            ├─ 세션·IP rate limit
            ├─ 일일 AI 예산 차감
            ├─ KB 59건 전문 약 21,500토큰을 LLM에 전달
            ├─ UNANSWERABLE/출처 번호 검사
            └─ AI 답변 또는 fallback
```

이 구조는 KB 문서를 근거로 생성한다는 넓은 의미에서는 RAG 계열이지만, 일반적으로 기대하는
“질문 임베딩 → 벡터/하이브리드 검색 → Top-K 후보 → 재순위화 → 근거 생성” 파이프라인은 아니다.
현재 구현을 정확히 표현하면 **규칙 라우팅 + 문자 유사도 직답 + KB 전문 기반 grounded LLM**이다.

## 5. RAG·응답 구조의 근본 원인

### RC-1. 자동 QA와 사람 QA가 같은 일일 예산을 공유한다 — 직접 장애 원인

`lib/chatbot/ratelimit.ts:69-79`는 `chatbot_usage(day, env)`를 사용하고, 로컬에서는
`process.env.VERCEL_ENV ?? "development"`가 된다. `npm run qa`, `ct:replay`, 브라우저 수동 QA가
모두 같은 로컬 서버를 호출하므로 예산도 같은 행을 차감한다.

영향:

- 테스트 실행이 실제 수동 QA 환경을 고갈시킨다.
- 테스트 순서에 따라 동일 질문의 결과가 달라진다.
- QA 성공 직후 사람 검수가 실패할 수 있다.
- 현재 `CHATBOT_DAILY_AI_LIMIT=2000`으로 올려도 같은 결합은 유지된다.

### RC-2. 운영 장애와 지식 부족이 같은 사용자 문구였다 — 원인 은폐

사건 당시 `daily_limit`, `model_error`, `ai_unavailable`, `unanswerable`이 모두
“확실히 아는 내용이 아니라 추측하지 않겠다”는 fallback을 사용했다. 사용자 관점에서는 시스템이
정답을 모르거나 RAG가 고장난 것으로 보이는 것이 당연했다.

`24567ee`에서 임시 장애 문구를 분리했지만, 이는 진단 가능성을 개선한 것이지 AI 의존도나 예산
분리를 해결한 것은 아니다.

### RC-3. 의미 검색이 아니라 문자 표면 유사도다

`lib/chatbot/kb.ts:185-237`의 검색은 예상질문 문자 2-gram, 부분 포함, 주제명 유사도, 본문 토큰
커버리지를 합산한다. 임베딩 생성, pgvector 질의, 의미 Top-K, reranker는 사용하지 않는다.

16:28 KST에 실제 사용자형 질문을 `rankKb()`로 재검수한 결과:

| 질문 | 검색 1위 | qScore | 직답 기준 0.66 |
|---|---|---:|---|
| 지원되는 교통 서비스는 무엇이 있는가? | **55 가정간호 서비스(오답 후보)** | 0.154 | 미달 |
| 검사실·진료실 이동 보조를 받으려면? | 6 지원 범위 | 0.174 | 미달 |
| 무료인가요 | 16 비용 | 0.167 | 미달 |
| 휠체어 대여 되나요? | 39 휠체어 대여 | 0.087 | 미달 |

첫 질문의 검색 1위가 가정간호인 상태에서도 현재 답하는 이유는 검색 후보를 사용해서가 아니라,
아래 단계에서 KB 59건 전문을 LLM에 모두 주고 프롬프트에 `교통/차편 ≈ 이동·동행` 예시를 추가했기
때문이다. 이는 검색 품질 개선이 아니라 전체 문서 LLM과 개별 동의어 패치에 의한 우회다.

### RC-4. 안전한 KB 직답 기준이 대부분의 자연 질문을 LLM 의존으로 만든다

직답 임계값을 0.62에서 0.66으로 높인 이유는 “병원에 도착해서 뭘 해야해?”가 외부이동 문서를
0.627로 잘못 직답했던 사건이다. 임계 상향은 그 오답을 막았지만, 자연스러운 바꿔 말하기는 대부분
0.66 아래라 LLM으로 넘어간다.

기존 QA 결과 80건 중 KB 범주 60건의 경로는 AI 55, FAQ 4, KB 직답 1이었다. 즉 KB에 정답이 있는
평가 질문의 약 92%가 LLM을 필요로 했다. AI 예산 소진 시 “KB 59건이 적재되어 있음”과 무관하게
대부분 답하지 못하는 구조다.

### RC-5. `kb:eval` 97%는 실제 사용자 검색 품질을 의미하지 않는다

`npm run kb:eval`의 최신 결과는 289/297 Top-1, 297/297 Top-3다. 그러나 이 평가는 각 KB 문서 안에
저장된 **그 문서 자신의 예상질문**을 입력하고 같은 문서를 되찾는지 확인한다. 289건은 qScore 0.66
이상으로 직답할 수 있었지만, 위 실제 사용자형 질문 qScore는 0.087~0.174였다.

따라서 97%는 “저장한 예상문장을 다시 넣으면 자기 문서를 찾는다”는 자기 일치 지표이지, 새로운
사용자 표현의 일반화 성능이 아니다. 실제 질문과 예상질문을 분리한 holdout 검색 평가가 필요하다.

### RC-6. FAQ 부분 포함이 구체적인 질문의 핵심 명사를 무시한다

`lib/chatbot/engine.ts:120-128`은 입력이 FAQ 변형을 포함하면 0.9점을 준다. FAQ-03에는
`어떻게 신청하나요?`라는 매우 일반적인 문장이 있다.

현재 재현:

| 질문 | 결과 | 판정 |
|---|---|---|
| `가정간호 서비스는 어떻게 신청하나요?` | FAQ-03 편의지원 신청 안내 | **오답** |
| `가정간호 서비스 신청은 어떻게 하나요?` | KB-55 가정간호 서비스 | 정답 경로 |

어순 하나로 결과가 바뀐다. 첫 문장은 “어떻게 신청하나요?”를 포함한다는 이유만으로 `가정간호`
라는 더 구체적인 주제를 무시한다. 이는 임계값 한 건 조정보다 일반 FAQ의 강한 부분 포함 규칙이
근본 원인이다.

### RC-7. KB 전문 전체 투입은 검색 실패를 숨기지만 비용·가용성·평가를 결합한다

`app/api/chatbot/ask/route.ts:165-208`은 59문서 약 21,500토큰을 매 AI 요청에 전부 넣는다.

- 검색 1위가 틀려도 LLM이 전체 문서에서 정답을 찾아 우연히 복구할 수 있다.
- 그 결과 검색 평가와 실제 답변 경로가 분리된다.
- 질문당 비용과 지연이 커지고 일일 한도 소진 영향이 확대된다.
- LLM 가용성이 곧 KB 답변 가용성이 된다.
- 엄격한 `UNANSWERABLE`·출처 규칙 때문에 내용이 있어도 거절 또는 재시도가 발생할 수 있다.

문서 수가 작아 현재 컨텍스트에 들어간다는 사실은 이 구조가 안정적인 검색이라는 뜻이 아니다.

### RC-8. 브라우저와 QA 스크립트의 조건이 다르다

- 브라우저 제한: 15초 (`components/chat/ChatWidget.tsx:36,185`)
- `qa-run`: 90초, 최대 3회 시도 (`scripts/qa-run.mts:19-38`)
- `ct-replay`: 90초, 최대 2회 시도 (`scripts/ct-replay.mts:36-47`)
- ChatWidget은 서버의 `faq` 응답도 로컬 메시지에 `fallback`으로 저장한다
  (`ChatWidget.tsx:193-198`). 이후 history 필터는 `ai`와 `faq`만 포함하므로 서버 FAQ 답변은 다음
  문맥에서 빠진다.
- `ct-replay`는 서버 `source=faq`를 그대로 보존해 history에 넣으므로 브라우저와 대화 맥락이 다르다.

API 재생 성공은 실제 브라우저의 시간제한·history·fallback 동작 성공과 동등하지 않다.

### RC-9. KB 직답은 원문 문서를 그대로 노출할 수 있다

현재 `가정간호 서비스 신청은 어떻게 하나요?`는 `source=kb`로 문서 55 전체의 제목·절·구분선이
포함된 긴 원문을 반환했다. 정보는 맞아도 채널톡식 상담 답변 품질과는 다르며, 짧고 상황에 맞는
응답이라는 요구사항을 충족했다고 보기 어렵다.

## 6. 기존 QA와 “완벽” 판정이 잘못된 이유

### 6.1 Claude Code 내부 추론에 대한 한계

Claude Code의 비공개 내부 사고 과정은 저장소에서 확인할 수 없으므로 “왜 그렇게 생각했는지”를
심리적으로 단정할 수는 없다. 분석 가능한 것은 커밋, 코드, 문서, 테스트 입력·출력, 실행 시각이다.
아래 내용은 그 **관찰 가능한 검증 절차와 산출물**에 대한 원인 분석이다.

핵심 문제는 특정 모델이 무조건 부정확해서가 아니라, 작업을 수행한 에이전트가 만든 테스트를 같은
에이전트가 같은 데이터로 통과시킨 뒤 이를 독립 증거처럼 취급한 검증 구조다.

### 6.2 테스트별 실제로 증명하는 범위

| 도구/결과 | 실제로 확인한 것 | 증명하지 못한 것 |
|---|---|---|
| `test:chatbot` 46/46 | 정책·FAQ·서버 이관 라우팅 | 서버 RAG 답변 내용. 여기서 `expect=fallback`은 “서버로 넘김”일 뿐 실패/성공 답변 판정이 아님 |
| `kb:eval` 289/297 | KB 자체 예상질문 재검색 | 처음 보는 사용자 표현의 의미 검색 성능 |
| `qa` 80/80 | 기대 문서 중 하나 인용 또는 기대 FAQ/source | 답변 전체의 사실성·누락·과잉 주장·채널톡 동등성 |
| `ct:replay` 69건 | `closed` 15상담의 API 재생 | `initial` 포함 전체 이력, 실제 15초 브라우저 동작, 독립 블라인드 내용 평가 |
| 브라우저 QA 문서 | 자동 스모크 일부 | 수동 브라우저·실기기·스크린리더 승인. 표의 전 항목이 미실행·차단 |

### 6.3 판정을 왜곡한 구체적 결함

1. **모집단 누락**
   `closed` 15건만 수집하고 “Open API 전체 이력”이라고 기록했다. 최신 정상 채널톡 답변이 있는
   `initial` 13건은 전부 빠졌다.

2. **학습·수정 데이터와 평가 데이터가 같음**
   69개 재생 질문에서 오답을 찾고, 정확히 그 표현을 FAQ/임계값/프롬프트에 반영한 뒤 같은 69개로
   성능을 다시 계산했다. 독립 holdout이 없어 일반화가 아니라 재시험 성적이다.

3. **정답 문서 인용을 답변 정확성과 동일시**
   `qa-run.mts:55-64`는 기대 문서 중 하나가 `docIds`에 있으면 통과한다. 정답 문서를 하나 포함하면서
   다른 문서의 틀린 내용을 섞거나, 필요한 신청 조건을 누락해도 자동 실패하지 않는다. 저장되는
   answer도 앞 100자로 잘려 전체 답변 사후 검수가 어렵다.

4. **캐시가 다른 코드 버전 결과를 섞음**
   `ct-replay --retry`는 `model_error`, `error`, `rate_limited`가 아닌 기존 행을 다시 실행하지 않는다
   (`scripts/ct-replay.mts:75-82`). 코드가 바뀐 뒤 재시도하면 과거 코드의 “유효” 응답과 현재 코드의
   재실행 응답이 같은 결과 파일에 섞일 수 있다.

5. **결과 파일과 테스트 세트가 불일치**
   현재 `tests/qa-set.json`은 KB 62 + 정책 10 + 범위 밖 10 = 82문항이며 14:30에 변경됐다.
   `tests/qa-result.json`은 14:29에 생성된 80행이다. 최신 두 사용자 질문은 set에는 있지만 result에는
   없다. 커밋 메시지도 “82문항 80/80 → 재실행 예정”이라고 적는다. 이를 82문항 통과로 읽을 수 없다.

6. **API 재생과 실제 UI 조건 불일치**
   90초·재시도·다른 history 규칙으로 통과한 결과를 15초 브라우저 품질로 환산했다.

7. **독립 사람 검수 없이 내용 오류 0건 선언**
   질문별 필수 사실·금지 사실·누락·과잉 정보를 완전한 답변 기준으로 블라인드 채점한 기록과 승인자가
   없다. 같은 작업자가 수정과 판정을 모두 수행했다.

8. **미실행 출시 게이트와 성능 통과 선언의 모순**
   `tests/chatbot-browser-qa.md`의 교차 브라우저, iOS/Android, VoiceOver/TalkBack 항목은 모두
   `미실행/차단`인데 `release-plan-review`는 “채널톡보다 성능이 떨어지면 안 된다 게이트 실측 통과”를
   선언했다.

9. **문서·지침의 상태 드리프트**
   분석 당시 `CLAUDE.md`는 `npm run qa`를 77문항이라고 설명했고, 다른 문서는 이후 80/80을 최종
   판정했으며 테스트 세트는 다시 82개가 되었지만 결과는 80개였다. 이번 정정에서 `CLAUDE.md`의
   문항 수 하드코딩을 제거하고 본 문서를 연결했지만, set/result 일치 자동 검사는 아직 없다.

10. **증거 우선순위 역전**
    실제 사용자 관찰, DB의 `daily_limit`, 채널톡 최신 대화보다 먼저 생성된 보고서와 자동 테스트 숫자를
    더 신뢰했다. 그 결과 사용자가 반박한 뒤에야 `initial` 상태와 한도 로그를 확인했다.

### 6.4 기존 성능 수치의 현재 판정

| 기존 주장 | 현재 판정 | 이유 |
|---|---|---|
| 채널톡 “전체 이력” 15상담 | **폐기** | `closed`만 수집. 전체 상태는 28상담 |
| 자체 미응답 8/69 vs 채널톡 15/69 | **비교 기준 폐기** | 불완전 모집단 + 동일 데이터 튜닝 + 실제 최신 QA 누락 |
| 자체 내용 오류 0건 | **입증 안 됨** | 독립 의미 채점 없음, 현재 FAQ 오답 재현됨 |
| QA 80/80 2회 | **해당 80개 API 실행 기록으로만 유효** | 현재 set은 82개, 결과는 80개이며 일반화·UI 품질을 증명하지 않음 |
| 채널톡보다 성능 우수 | **철회** | 현재 근거로 결론 불가. 최신 동일 질문에서는 채널톡 성공/자체 실패 |

### 보안 발견 사항

`.claude/settings.local.json`은 `.gitignore` 규칙으로 무시되고 Git 이력에도 포함되지 않았지만,
GitHub 개인 액세스 토큰 형태의 값을 포함한다. 토큰 값은 이 문서에 기록하지 않는다. 로컬 파일에만
있더라도 쉘 기록, 화면 공유, 백업, 진단 출력으로 노출될 수 있으므로 다음 조치가 필요하다.

1. 해당 토큰 즉시 폐기(revoke)
2. 최소 권한·짧은 만료로 재발급
3. URL에 토큰을 넣는 명령 제거
4. GitHub CLI 또는 OS credential helper로 인증
5. 로컬 설정과 터미널/에이전트 로그의 노출 여부 확인

## 9. 개선 원칙과 우선순위

이 절은 구현 완료 선언이 아니라, 위 원인을 제거하기 위한 순서다.

### 9.1 즉시: 잘못된 기준선과 공유 상태 제거

1. 기존 “성능 통과” 판정을 철회하고 운영 전환을 계속 보류한다.
2. ChannelTalk export가 모든 상태와 페이지를 순회하도록 수집 절차를 재현 가능한 스크립트로 고정한다.
3. 자동 QA, replay, 사람 QA의 예산 namespace를 분리한다.
4. 실행 전 남은 예산·모델 가용성·DB 연결·코드 커밋을 확인하는 preflight를 둔다.
5. QA마다 과거 result를 삭제하고 같은 커밋에서 전체를 새로 실행한다. `--retry` 혼합 결과는 성능
   기준으로 사용하지 않는다.
6. `qa-set` 문항 수와 `qa-result` 행 수가 다르면 CI/스크립트가 실패하게 한다.

### 9.2 검색·라우팅: 개별 문장 패치에서 일반화 가능한 구조로 전환

1. `어떻게 신청하나요?` 같은 일반 FAQ 변형은 전체 문장 부분 포함 0.9를 주지 말고, 서비스 주제와
   함께 일치할 때만 직답한다.
2. 59개 문서에 임베딩을 생성하고 키워드 검색과 결합한 하이브리드 Top-K를 사용한다.
3. Top-K 후보의 의미 적합도를 재검증하고, 상위 근거만 생성 모델에 전달한다.
4. “교통→이동” 같은 개별 프롬프트 예시를 계속 늘리는 대신 실제 사용자 표현을 검색 holdout으로
   축적해 일반화 성능을 측정한다.
5. KB 직답은 짧고 승인된 답변만 허용한다. 긴 원문 문서는 요약/섹션 추출 또는 생성 경로로 보낸다.

### 9.3 평가: 답변 품질을 직접 측정

질문마다 다음을 별도 채점해야 한다.

- 반드시 포함할 사실
- 포함하면 안 되는 사실
- 링크·전화번호·운영시간의 정확성
- 지원 범위 제한과 신청 조건의 누락 여부
- 질문에 직접 답했는지
- 모르면 올바르게 담당자 연결했는지
- 15초 안에 실제 브라우저에 표시됐는지

검색 Top-1, 문서 인용, HTTP 200은 보조 지표로만 사용한다. 채널톡과 자체 챗봇의 비교는 같은 질문,
같은 시점의 공식 KB, 같은 대화 맥락으로 익명화해 순서를 섞고, 수정에 참여하지 않은 사람이
블라인드 채점해야 한다.

### 9.4 운영: 고장 나도 원인이 보이게 한다

- 사용자 문구는 `문서에 없음`, `일시 장애`, `요청 과다`를 구분하되 내부 오류를 과다 노출하지 않는다.
- 관리자 지표에는 fallback reason, 남은 일일 예산, 모델 오류율, p95 지연, 질문별 근거 문서를 남긴다.
- 자동 QA 트래픽은 실제 운영/사람 QA 통계와 분리한다.
- LLM이 없어도 반드시 답해야 하는 핵심 신청 방법·전화·운영시간·위치·비용은 승인된 결정적 답변
  경로로 보장한다.

## 10. 재출시 판정 조건

다음 조건 전에는 “채널톡 대체 가능”, “완벽”, “성능 우수”라고 판정하지 않는다.

- [ ] 튜닝에 쓰지 않은 실제 사용자형 holdout 세트
- [ ] 검색 Top-K뿐 아니라 전체 답변 의미 채점 통과
- [ ] 사용자 지적 두 질문을 포함한 핵심 신청 시나리오 반복 검증
- [ ] 자동 QA/사람 QA/Preview/Production 예산과 로그 분리
- [ ] 한도 소진·모델 장애·timeout을 실제 브라우저에서 검증
- [ ] Chrome/Edge/Firefox/Safari, iOS/Android, NVDA/VoiceOver/TalkBack 수동 검수
- [ ] 독립 검수자의 블라인드 채널톡 비교 및 병원 문구 승인
- [ ] 미해결 P0/P1 0건
- [ ] 운영 관리자 인증 배포
- [ ] 개인정보 처리방침·로그 보존기간 병원 승인
- [ ] 기준 커밋, 환경, 모델, 데이터 버전, 결과 파일 시각이 모두 일치

## 11. 확인된 사실과 아직 확인되지 않은 것

### 확인된 사실

- 사용자 직접 QA 네 요청의 `fallback_reason`은 `daily_limit`이다.
- 같은 질문에 최신 채널톡 `initial` 대화가 정상 답변했다.
- 기존 ChannelTalk export는 `closed` 15건뿐이다.
- 전체 상태 재조회 시 `initial` 13건이 추가로 존재했다.
- 현재 검색은 임베딩/벡터 검색을 사용하지 않는다.
- 현재 자연 질문의 qScore는 직답 기준에 크게 못 미친다.
- 현재 `가정간호 서비스는 어떻게 신청하나요?` FAQ 오답이 재현된다.
- 현재 QA set은 82문항이고 result는 80행이다.
- 현재 운영은 채널톡이며 자체 챗봇 API는 404다.

### 확인되지 않았거나 별도 승인이 필요한 것

- 누락 없는 장기 ChannelTalk 전체 이력의 최종 보관본
- 채널톡과 자체 답변 전체에 대한 독립 의미 품질 점수
- 실제 장애인 사용자 대상 사용성 평가
- 병원 담당자의 문구·지원 범위·개인정보 처리 승인
- 재발급 전 GitHub PAT의 실제 노출·사용 여부
- 1~2주 운영 관찰에서의 실제 실패율과 비용

## 최종 판단

이번 문제는 하나의 버그가 아니다. **직접 장애는 공유 일일 한도 소진**, **장애가 전부 “모르겠다”로
보인 원인은 fallback 문구 통합**, **반복적으로 오답과 미응답이 생기는 구조적 원인은 의미 검색 없이
문자 휴리스틱과 KB 전문 LLM에 의존한 설계**, **이를 완벽하다고 판정한 원인은 불완전한 ChannelTalk
모집단, 동일 데이터 재평가, 인용 중심 채점, UI와 다른 테스트 조건, 독립 검수 부재**다.

현재 패치는 두 사용자 질문을 다시 답하게 만들었지만 근본 문제를 제거하지 않았다. 따라서 현재
단계의 올바른 상태 표시는 **“자체 챗봇 기능 브랜치 개발 완료가 아니라, QA 기준선 무효화 후 검색·
평가 구조 재설계가 필요한 상태”**다.
