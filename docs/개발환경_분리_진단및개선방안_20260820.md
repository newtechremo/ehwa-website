# dev/prod 환경 분리 — 진단 및 개선 방안

- 작성일: 2026-08-20
- 관련: `docs/챗봇_자체구축_통합구현플랜_20260820.md` 4장(dev 환경 설계) 수정 근거
- 계기: "왜 별도 Supabase dev 프로젝트가 필요한가, 로컬에서 하면 안 되는가"

---

## 1. 결론 요약

**별도 클라우드 dev 프로젝트는 필요 없다. 로컬 Supabase로 충분하다.**
다만 그보다 **훨씬 심각한 환경 분리 문제**가 따로 있다 —
**개발 작업 디렉토리와 레거시 운영 서버 디렉토리가 같은 폴더다.**

| # | 문제 | 심각도 | 현재 실사용자 영향 |
|---|---|---|---|
| 1 | 개발 디렉토리 = PM2 운영 서버 디렉토리 | **P0** | 없음(트래픽 0) — 잠재 위험 |
| 2 | GitHub Actions가 main push 시 작업트리를 `git stash` | **P0** | 없음 — 개발자 작업 유실 위험 |
| 3 | 로컬·Preview·Production 전부 같은 운영 Supabase | **P0** | 없음 — 운영 데이터 오염 위험 |
| 4 | 로컬 Supabase 미구성 | P1 | — |
| 5 | Vercel이 Git 연동이 아니라 CLI 수동 배포 | P1 | 재현성 없음 |

## 2. 진단 상세

### 2.1 [P0] 개발 디렉토리 = 레거시 운영 서버 디렉토리

```
PM2 ehwa-website  exec cwd = /home/finefit-temp/Desktop/project/ehwa_website
개발 세션          작업 dir = /home/finefit-temp/Desktop/project/ehwa_website   ← 동일
```

- PM2는 `npm run start`(= `next start`)로 **같은 폴더의 `.next/`를 서빙**한다.
- 이번 세션에서 실행한 `npm run build` 4회가 그 `.next/`를 그대로 덮어썼다.

**증거**

| 항목 | 값 |
|---|---|
| PM2 프로세스 시작 | 2026-08-18 17:39 (46시간 전, 재시작 1회) |
| `.next/BUILD_ID` 갱신 | **2026-08-20 15:18** (수분 전, 개발 빌드) |

즉 **메모리에 뜬 빌드와 디스크의 빌드가 서로 다른 상태**다.
`localhost:3112`는 여전히 구 빌드(채널톡)를 응답하지만, PM2가 재시작되는 순간
디스크에 있는 **개발 브랜치 빌드가 그대로 기동**된다.

추가로 포트 3112를 PM2가 점유 중이라 `npm run dev`(기본 3112)가 **바로 충돌**한다.
"로컬에서 개발하면 되지 않나"가 지금 당장 안 되는 실제 이유다.

> 현재 실사용자 영향은 0이다. DNS(`76.76.21.21`)가 Vercel을 가리키므로 이 서버는 트래픽을 받지 않는다.
> 그러나 잠재 위험이며, 무엇보다 **로컬 개발을 시작할 수 없게 만드는 직접적 장애물**이다.

### 2.2 [P0] GitHub Actions가 개발 작업트리를 조작

`.github/workflows/deploy.yml` — `main` push 시 SSH로 접속해 실행:

```bash
cd /home/finefit-temp/Desktop/project/ehwa_website   # ← 개발 작업 디렉토리
git stash
git pull origin main
git stash pop || true                                 # ← 충돌해도 무시하고 진행
npm install && npm run build && pm2 restart ehwa-website
```

- 누군가 main에 push하면 **개발 중인 작업트리가 stash 되고 pull 된다.**
- `|| true` 때문에 stash pop 실패(충돌)도 조용히 넘어간다 → 작업 유실 가능.
- 폐기 예정인 레거시 서버에 계속 배포한다.
- 챗봇 코드가 main에 머지되는 순간 이 서버에도 자동 배포된다.

### 2.3 [P0] 모든 환경이 같은 운영 Supabase를 가리킴

| 환경 | Supabase 대상 |
|---|---|
| 로컬 `.env.local` | **운영** (`jfkevhtdiicrmytmwyes`) |
| Vercel `development` | **운영** |
| Vercel `preview` | **운영** |
| Vercel `production` | 운영 |

**dev/prod DB 분리가 전혀 없다.** 지금 상태로 `npm run dev`를 돌리면
로컬 개발이 운영 DB에 직접 쓴다. Phase A는 신규 로그 테이블뿐이라 무해했지만,
Phase B(KB 적재·재색인)에서는 그대로 두면 안 된다.

### 2.4 [P1] 로컬 Supabase 미구성

| 항목 | 상태 |
|---|---|
| Docker | **실행 중** (`/usr/bin/docker`, 데몬 동작) |
| Supabase CLI | 미설치 |
| `supabase/config.toml` | 없음 (`supabase init` 미실행) |
| `supabase/migrations/` | **있음** (init 1건 + chatbot 1건) |

즉 **CLI 설치 + `supabase init` 만으로 즉시 로컬 DB를 띄울 수 있는 상태**다.

### 2.5 [P1] Vercel이 Git 연동이 아님

프로덕션 배포가 `vercel --prod` CLI 수동 실행이다. 그 결과:

- **어떤 커밋이 프로덕션인지 git에서 확인할 수 없다.**
- 실제로 keepalive cron은 **미커밋 작업트리 상태에서 프로덕션에 배포**됐다(이후 커밋으로 정리).
- 브랜치 → 환경 매핑이 없어 preview 배포도 수동이다.

## 3. 목표 구조

```
┌ 로컬 개발 ─────────────────────────────────────────────┐
│ npm run dev (포트 3112)                                │
│   └→ Supabase 로컬 (Docker)  ← 운영과 완전 격리        │
│ npm run test:chatbot          ← DB 불필요 (순수 로직)  │
│ supabase db reset             ← 마이그레이션 검증      │
└────────────────────────────────────────────────────────┘
                    │ push (feat/*)
┌ Vercel Preview ───▼────────────────────────────────────┐
│ 목적: ①담당자 검수용 URL ②프로덕션 빌드 검증           │
│   └→ 운영 Supabase + env 컬럼 분리                     │
│      (챗봇 테이블은 신규 테이블, 프로덕션 코드가 안 읽음)│
└────────────────────────────────────────────────────────┘
                    │ merge → main
┌ Vercel Production ▼────────────────────────────────────┐
│ barrierfree.eumc.ac.kr → 운영 Supabase                 │
│ NEXT_PUBLIC_CHATBOT_ENABLED 미설정 = 채널톡 유지        │
└────────────────────────────────────────────────────────┘

레거시 PM2 서버 → 폐기
```

**핵심 판단: Preview까지 별도 DB를 줄 필요는 없다.**
Preview의 목적은 "보여줄 URL"과 "빌드 검증"이지 데이터 격리가 아니다.
데이터 격리가 진짜 필요한 곳은 **스키마를 깨뜨려 가며 실험하는 로컬**이고, 거기는 로컬 Supabase가 담당한다.

## 4. 실행 방안

### 단계 1 — 레거시 PM2 서버 정리 [P0, 선행]

로컬 개발을 시작하려면 이게 먼저다. 포트와 디렉토리를 둘 다 점유하고 있다.

1. 무트래픽 확인 — DNS가 Vercel(`76.76.21.21`)을 가리키는지 재확인
2. `.github/workflows/deploy.yml` **먼저** 비활성화 (안 그러면 main push가 서버를 되살림)
3. `pm2 stop ehwa-website` → 며칠 관찰 → `pm2 delete ehwa-website` + `pm2 save`
4. 백업 보존 확인 (`~/ehwa_backup_20260608/`)

> 되돌리기: `pm2 start npm --name ehwa-website -- run start` + DNS A레코드 원복

### 단계 2 — 로컬 Supabase 구성 [P0]

```bash
npm i -D supabase          # 또는 공식 설치 스크립트
npx supabase init          # config.toml 생성
npx supabase start         # Docker로 Postgres + Studio 기동
npx supabase db reset      # migrations/ 전체 적용 검증
```

- `.env.local`을 **로컬 Supabase 키**로 교체 (`supabase start` 출력의 API URL / anon / service_role)
- `.env.local`에 `NEXT_PUBLIC_CHATBOT_ENABLED=true` 추가
- 운영 키는 `.env.production.local` 등으로 분리 보관하거나 아예 로컬에서 제거
- `.env.example`을 로컬 기준으로 갱신

**부수 효과: 마이그레이션 검증이 정석대로 된다.** 지금은 Management API로 운영 DB에
직접 SQL을 던지고 있는데(chatbot 마이그레이션이 그랬다), 앞으로는
로컬 `db reset` → 통과 → 운영 적용 순서를 강제할 수 있다.

### 단계 3 — Vercel Git 연동 전환 [P1]

- GitHub 저장소를 Vercel 프로젝트에 연결
- `main` = Production, 그 외 브랜치 = Preview 자동 생성
- 효과: **미커밋 상태 배포가 구조적으로 불가능해지고**, 커밋 ↔ 배포가 1:1로 추적된다
- **단계 1(deploy.yml 비활성화)이 반드시 선행돼야 한다** — 안 그러면 main push가 레거시 서버도 함께 깨운다

### 단계 4 — Phase B DB 결정 [P1] → **결론: 추가 비용 불필요**

앞서 P1 결정사항으로 올렸던 "Supabase Pro 전환 / `woosung-hr-billing` 정리 / env 분리 감수"는
**세 가지 모두 불필요**하다.

- 스키마 개발·임베딩 실험·재색인은 **로컬 Supabase**에서 한다
- Preview는 완성된 KB를 읽기만 한다. KB 테이블은 신규 테이블이고 프로덕션은 챗봇이 flag off라 실사용자 영향 0
- 운영 DB에 남는 리스크는 재색인이 Free 인스턴스 리소스를 점유하는 정도인데, 59문서 규모면 미미하다

## 5. 개발 방식 개선

| 항목 | 현재 | 개선 |
|---|---|---|
| 마이그레이션 | Management API로 운영 DB에 직접 SQL | 로컬 `db reset` 검증 → preview → production |
| 배포 | `vercel --prod` 수동 (작업트리 상태) | Git push 기반, 커밋 = 배포 단위 |
| 로컬 실행 | 포트 충돌로 불가 | `npm run dev` 정상 동작 |
| 환경변수 | 4개 환경 모두 운영 DB | 로컬만 분리, Preview/Prod는 운영 공유(의도적) |
| 테스트 | `npm run test:chatbot` (DB 불필요) | 유지 + Phase B에서 골든셋 추가 |
| 스크립트 | build/dev/start/lint/test:chatbot | `db:start`, `db:reset` 추가 |

## 6. 우선순위

| 순서 | 작업 | 차단 요소 |
|---|---|---|
| 1 | `deploy.yml` 비활성화 | 없음 |

| 4 | Vercel Git 연동 | 1 선행 |
| 5 | Phase B 착수 (KB 자산 수령 시) | 3 선행 |

**1~3은 되돌리기 쉬운 작업이며, 실사용자 영향이 없는 지금이 정리 적기다.**
