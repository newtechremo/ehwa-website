### 1.2 keepalive cron (완료·배포됨)

- 신규 파일: `app/api/cron/keepalive/route.ts`
- `vercel.json`에 `crons` 추가 — `path: /api/cron/keepalive`, `schedule: 0 3 * * *` (UTC 03:00 = KST 12:00)
- `CRON_SECRET` 환경변수 등록 (Vercel Production). Vercel Cron이 자동으로 `Authorization: Bearer` 헤더를 붙인다.
- 동작 검증:
  - 인증 없이 호출 → `401 {"error":"Unauthorized"}`
  - 인증 포함 → `200 {"ok":true,"posts":7}`
  - Vercel API로 cron 등록 확인 (`enabledAt` 설정, `disabledAt: null`)

> 남은 위생 작업: 현재 변경은 커밋 전 상태다. `vercel.json` + `app/api/cron/` 를 커밋해야 다음 배포에서도 유지된다.

## 2. 채널톡 401 — 진단 결과 (정정 포함)

### 2.1 결론: 채널톡은 정상 작동 중이다

앞선 세션에서 "채널톡이 라이브에서 뜨지 않는다"고 판단했으나, **잘못된 결론이었다.**
자격증명이 전혀 없는 신규 방문자로 boot을 재현하면 **200**이 나온다.

```
POST https://api.channel.io/front/v8/elastic/plugins/{key}/boot
Content-Type: application/x-www-form-urlencoded
body: url=https%3A%2F%2Fbarrierfree.eumc.ac.kr%2F
→ 200, sessionJWT + veilId 발급
```

### 2.2 401이 났던 진짜 이유

- 401 응답 본문: `{"type":"unauthenticatedError","errors":[{"message":"Your credentials have changed and you have been logged out."}]}`
- 채널톡은 방문자 세션 쿠키를 **`cookieDomain: .eumc.ac.kr`** 에 심는다 (boot 응답에 명시).
- 테스트 브라우저 프로필에 **무효화된 기존 세션 쿠키**가 남아 있었고, 그 쿠키가 401을 유발했다.
- 해당 쿠키는 **HttpOnly** 라 `document.cookie` 로 지워지지 않아, localStorage를 비우고 새로고침해도 401이 재현됐다.

### 2.3 그래도 남는 실제 리스크

테스트 환경에서 관찰된 현상은 **재현 가능한 사용자 영향 시나리오**다.

> 과거에 방문해 세션 쿠키를 갖고 있고 그 세션이 무효화된 재방문자는, boot 401을 받고
> **런처 버튼이 렌더링되지 않으며, 새로고침해도 자가 복구되지 않는다.**

즉 "챗봇 전면 장애"는 아니지만 "일부 재방문자에게 챗봇이 안 보이는" 상태는 실재한다.

### 2.4 401 원인 확인 절차 (재현·진단 방법)

| # | 방법 | 판정 |
|---|---|---|
| 1 | **신규 방문자 재현 (curl)** — 쿠키 없이 boot POST (`x-www-form-urlencoded`, body `url=...`) | 200이면 채널·플랜 정상. 401이면 채널 레벨 문제 |
| 2 | **플러그인 공개 설정 조회** — `GET .../front/v8/elastic/plugins/{key}` | `state`, `channelId`, 버튼 설정 확인 |
| 3 | **boot 응답의 채널 플래그 확인** | `state`, `blocked`, `working`, `workingType` |
| 4 | **브라우저 시크릿창 / 새 프로필** 로 접속 | 뜨면 쿠키 문제, 안 뜨면 채널 문제 |
| 5 | **쿠키 완전 삭제** — 개발자도구 Application → Cookies → `.eumc.ac.kr` 전체 삭제 후 새로고침 (HttpOnly라 JS로는 불가) | 정상화되면 원인 확정 |
| 6 | **채널톡 콘솔** — 구독/결제 상태, 채널 휴면 여부, 허용 도메인 설정 확인 | 계정 레벨 확인 |

## 3. 채널톡 기능 구성 전체 분석

### 3.1 코드 결합도 — 매우 얕다 (파일 2개 / 약 15줄)

| 위치 | 내용 |
|---|---|
| `app/layout.tsx:80-93` | SDK 인라인 스니펫 + `ChannelIO('boot', { pluginKey })` — **익명 boot**, 사용자 식별·프로필·해시인증 없음 |
| `app/admin/layout.tsx:32-45` | `hideChannelButton` / `showChannelButton` (관리자 화면에서 숨김) |

`openChat`, `track`, `updateUser`, `onBadgeChanged` 등 고급 API 미사용. 서버 연동·웹훅·API 키·환경변수 없음.

### 3.2 그러나 실제 기능은 전부 채널톡 콘솔 안에 있다

인수인계 문서 기준, 현행 챗봇은 **버튼형 시나리오 + FAQ + RAG 하이브리드**다.

| 계층 | 구성 | 규모 |
|---|---|---|
| 버튼형 시나리오 | 1차 6버튼 (지원범위/이용대상/신청방법/비용안내/운영시간&위치/질문하기) + 신청방법 5분기 | 노드 10여 개 |
| FAQ | 대표질문 + 유사질문 `question1~11` + 단일 `answer` | **44건** |
| RAG 지식문서 | 편의지원 43건 + 병원 일반 16건 | **59건** |
| AI 정책 | 역할·말투·금지사항·Fallback (`00_AI_INSTRUCTION_v2.md`, `inepector.txt`) | 시스템 프롬프트 |
| 정책 분기 | 의료진단 / 병원민원 / 보험·병원비 / KB부재 / 개인정보 | 5분류 |
| 외부 연결 | Walla 신청서, 카카오톡, 전화 `02-2650-5586`, 이메일, 방문 | 5경로 |

**핵심 판단: 교체 비용은 코드가 아니라 콘텐츠·엔진 재현에 있다.**
스니펫 15줄을 지우는 건 5분이지만, 시나리오 10노드 + FAQ 44 + KB 59 + 정책 5분류를
동등한 품질로 재현하는 것이 실제 작업량이다.

### 3.3 자체구축 시 사라지는 것 / 얻는 것

| | 잃는 것 | 얻는 것 |
|---|---|---|
| 운영 | 상담원 인박스·모바일앱·알림, 통계 대시보드 (직접 만들어야 함) | 데이터 소유, 벤더 종속 해소 |
| 비용 | — | 채널톡 구독료 절감 (AI 상담 플랜은 특히) |
| 접근성 | — | **cross-origin iframe 탈출** — 아래 3.4 |
| 안정성 | 채널톡 SLA | 401 세션 이슈 같은 블랙박스 장애 제거 |

### 3.4 접근성 — 자체구축의 결정적 근거

채널톡 위젯은 `api.channel.io` **cross-origin iframe** 이다.

| A11yBar 기능 | 사이트 본문 | 채널톡 위젯 내부 |
|---|---|---|
| 고대비 (`body.low-vision`, `styles/main.css:136-160`) | O | **X — 적용 불가** |
| 글자확대 (`documentElement.style.fontSize` 125/150%) | O | **X — 적용 불가** |
| 수어 토글 (`signLanguageEnabled`) | O | **X — 연동 불가** |
| 포커스 순서·스크린리더 레이블 제어 | O | **X** (현재 레이블 `title="Channel chat"` 영문) |

장애인 이용편의 지원센터 사이트에서 상담 창구만 접근성 사각지대다.
**다른 SaaS로 갈아타도 iframe인 한 동일**하므로, 이 요구사항은 자체구축으로만 충족된다.

## 4. dev 환경 설계

### 4.1 현재 구조의 문제

- Vercel 프로젝트 1개, **Production 환경만 사용** (Preview 배포 이력 없음)
- Supabase 프로젝트 1개 = **운영 DB**. 챗봇은 KB·대화로그 테이블 신설이 필요한데 운영 스키마를 직접 건드리게 됨
- 로컬 PM2 서버가 아직 가동 중 (`ehwa-website`, nginx) — 같은 운영 Supabase를 바라봄
- 테스트 프레임워크 없음 (`package.json`에 test script/vitest/playwright 없음)

### 4.2 권장안 — 옵션 1: Vercel Preview + 별도 Supabase dev 프로젝트

```
main ─────────────────────► Vercel Production ──► Supabase prod (jfkevhtdiicrmytmwyes)
                                                   barrierfree.eumc.ac.kr

feat/chatbot ─────────────► Vercel Preview ─────► Supabase dev (신규 생성)
                            (브랜치별 URL 자동)     운영 데이터 무관
```

| 항목 | 내용 |
|---|---|
| Supabase dev | 신규 프로젝트 `ehwa-website-dev`, 리전 **ap-northeast-2(서울)** 고정. 조직당 Free 2개까지 가능하므로 **추가 비용 0** |
| Vercel 환경 | Preview 환경변수에 dev Supabase 키 3종 + `CRON_SECRET` 등록 |
| 브랜치 | `feat/chatbot` 신설 (현재 `feat/supabase-migration` 기준) |
| 마이그레이션 | `supabase/migrations/` 에 챗봇 스키마 추가 → dev 먼저 적용 → 검증 후 prod |
| 시드 | KB 59건·FAQ 44건 적재 스크립트를 `scripts/` 에 두고 dev에서만 실행 |
| pause 대비 | **dev 프로젝트에도 keepalive 필요하나 Vercel Cron으로는 불가** — Vercel Cron은 Production 배포에서만 실행된다. 대안: GitHub Actions `schedule` 워크플로로 dev Supabase REST에 주기 ping (레포에 이미 Actions 사용 중), 또는 개발 중단 시 수동 restore 감수 |

### 4.3 대안 비교

| 옵션 | 장점 | 단점 | 판정 |
|---|---|---|---|
| **1. Preview + dev Supabase** | 격리 완전, 비용 0, PR 미리보기 URL, 랜딩과 통합 테스트 가능 | Free 2개 pause 관리 | **권장** |
| 2. 별도 Vercel 프로젝트 | 완전 격리 | 챗봇은 랜딩에 붙어야 하는데 통합 검증이 어려움 | 비권장 |
| 3. 같은 Supabase에 `chatbot` 스키마 분리 | 관리 최소 | 운영 DB에 개발 중 스키마가 섞임, 사고 시 운영 영향 | 비권장 |

### 4.4 운영 안전장치

- **feature flag**: `NEXT_PUBLIC_CHATBOT_ENABLED` 로 신규 위젯 노출 제어. Production은 기본 off
- **병행 운영**: 자체 챗봇이 검수를 통과할 때까지 채널톡 스니펫 유지 → 전환 시 한 줄 교체
- **롤백**: 스니펫 복구 + flag off 두 가지 경로 확보

## 7. 테스트 전략

현재 레포에 테스트 프레임워크가 없다. **Vitest(단위·엔진) + Playwright(E2E·접근성)** 도입을 전제로 한다.

### 7.1 시나리오 회귀 (문서 11장 체크리스트 자동화)

문서 11장 13개 항목을 그대로 E2E 케이스로 변환. 예:
- 첫 화면 빠른선택 버튼 6개 노출
- 모든 흐름에서 `처음으로`/`질문하기` 도달 가능
- 신청방법 → 신청서·카카오톡·전화·이메일·방문 5경로 연결
- 전화번호 `02-2650-5586` 과 Walla URL이 **모든 경로에서 동일**

### 7.2 RAG 골든셋 (핵심)

- 59개 지식문서 × 대표질문 1개 = **59 케이스**
- 자동 채점: 답변에 사용된 **근거 문서 ID가 정답 문서와 일치**하는지 (Top-1 / Top-3)
- 제안 목표치: **Top-1 ≥ 85%, Top-3 ≥ 95%** — 문서에는 수치 목표가 없어 보완 필요

### 7.3 정책 가드 테스트

| 분류 | 케이스 수 | 기대 동작 |
|---|---|---|
| 의료 진단·처방 | 5 | 진단 생성 금지 → 의료진 안내 |
| 병원 민원·불만 | 5 | 사과 + 대표번호 |
| 보험·병원비 | 5 | 범위 밖 고지 + 원무 안내 |
| 개인정보 요구 | 5 | 수집 거부 + 별도 채널 |

**프롬프트가 아니라 코드 레벨 분류기로 구현**하고, 프롬프트는 2차 방어선으로 둘 것.

### 7.4 환각(hallucination) 테스트

문서 10장 "검토 대기 질문" 4건 — 장애인 콜택시 하차 위치 / 발작 후 안정 공간 / 안내견 출입 / 장루 세척 가능 화장실.
→ **하드 차단 목록**으로 구현하고, 반드시 "담당자 확인 후 안내"로 빠지는지 검증.
