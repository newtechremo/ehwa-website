## 0. 확정된 설계 원칙

1. **하나의 위젯, 하나의 대화 스트림.** 버튼 시나리오·FAQ·AI 자유질문·연결 카드는 별개 화면이 아니라
   채널톡과 동일하게 **한 채팅창 안에서 섞여 동작**한다. 버튼 클릭도, AI 답변도 같은 말풍선 스트림에 쌓인다.
2. 단계(Phase)는 **위젯을 나눠 만드는 것이 아니라 AI 모듈을 언제 켜는가**의 차이다.
   Phase A부터 입력창을 포함한 완성형 위젯이 나간다.
3. AI 없이도 챗봇의 대부분(버튼·FAQ·연결)이 동작해야 한다. AI 장애·한도초과 시 자동 강등.
4. 접근성 우선: A11yBar(고대비·글자확대·수어)와 완전 연동 — iframe 금지, 사이트 DOM 내부 렌더.
5. 전화번호·카카오·Walla URL은 하드코딩 금지 (설정 데이터).

## 2. 아키텍처 (현 시스템 위에)

```
app/layout.tsx (flag: NEXT_PUBLIC_CHATBOT_ENABLED)
 └─ <ChatWidget/>                       ← 사이트 DOM 내부. iframe 아님
     ├─ ChatLauncher   플로팅 버튼 + 라벨 (z-[1900]: Header 1500 < 위젯 < A11yBar 2000)
     └─ ChatPanel      role="dialog" aria-modal, 포커스 트랩, ESC 닫기
         ├─ ChatHeader     봇 이름·아바타·닫기 (#004c28)
         ├─ MessageList    말풍선 스트림, aria-live="polite"
         │   ├─ BotBubble / UserBubble
         │   ├─ QuickReplies   버튼 칩 (시나리오 네비게이션)
         │   └─ ActionCard     tel: / 카카오 / Walla / 링크
         └─ ChatInput      자유질문 입력 (Phase A부터 존재)

클라이언트 엔진 (lib/chatbot/)
 ├─ content.ts      시나리오 노드·버튼·FAQ·액션·문구 = 타입 있는 데이터 (Phase C에서 DB로 이관)
 ├─ engine.ts       입력 라우팅: ①버튼 → 노드 전이 ②텍스트 → FAQ 매칭 ③실패 → AI 또는 연결 카드
 └─ faq-match.ts    정규화(공백·조사 단순화) + 키워드 매칭. LLM 불사용

서버 (app/api/chatbot/)
 ├─ ask/route.ts    [Phase B] AI 자유질문. 스트리밍. AI Gateway "provider/model" (env CHATBOT_MODEL)
 │                   가드 파이프라인: 사전분류(하드차단) → 시스템프롬프트 → 근거문서 ID 사후검증
 │                   제한: 입력 500자, maxOutputTokens, 세션·IP rate limit, 일일 서킷브레이커
 └─ log/route.ts    [Phase A] 대화 로그 적재 (버튼 경로·질문·FAQ 히트·fallback 여부)

Supabase (기존 prod/dev 프로젝트)
 ├─ chatbot_logs        Phase A부터. fallback 질문 수집 = KB 개선 입력 (원본 문서 9장 흐름)
 ├─ chatbot_usage       일일 AI 호출 카운터 (서킷브레이커 근거)
 └─ kb_documents/kb_chunks  Phase B (검색 방식은 골든셋 비교 후: LLM 라우터 우선 검토)
```

**현 시스템 재사용:** shadcn/ui(dialog·button·scroll-area 등 설치 완료), Tailwind 4, Pretendard,
`styles/main.css`의 `body.low-vision *` 전역 오버라이드(위젯이 DOM 내부이므로 **자동 상속**),
`useAccessibility`의 `fontSize` 스케일(rem 기반이면 자동 반영 — 위젯 CSS는 px 대신 rem 사용),
기존 `/api/*` 상대경로 fetch 패턴, `lib/db.ts` service_role 패턴.

**콘텐츠를 Phase A에서 DB가 아닌 `content.ts`로 두는 이유:**
노드 10개+FAQ 44건은 수 KB다. 코드와 함께 git으로 버전관리되고, 배포 즉시 반영되며, 타입체크를 받는다.
관리자 CRUD(Phase C)가 생길 때 같은 스키마로 Supabase에 이관한다 — 엔진은 데이터 출처만 바뀌고 그대로.

## 3. 대화 흐름 (엔진 라우팅 규칙)

```
사용자 입력
 ├─ 버튼 클릭 ────────────────► 노드 전이, 고정 답변 + 다음 버튼칩         (LLM 없음)
 └─ 텍스트 입력
     ├─ ① 하드차단 매칭 (의료진단·민원·보험·개인정보 + 검토대기 4건)
     │        └─► 정책 고정답변 + 연결 카드                                (LLM 없음)
     ├─ ② FAQ 매칭 (44건, 유사질문 포함 키워드 매칭)
     │        └─► FAQ 고정답변 + 후속 버튼                                 (LLM 없음)
     ├─ ③ [Phase B] AI 라우팅 — KB 문서 선택 → 근거 기반 생성 → 근거 ID 사후검증
     │        ├─ 검증 통과 ─► 스트리밍 답변 + 출처 + 후속 제안
     │        └─ 근거 없음 ─► ④로
     └─ ④ Fallback ─► "담당자 확인 후 안내" + 전화·카카오 카드 + 로그 기록
                        (Phase A에서는 ③이 없으므로 ②실패 = 바로 ④)
```

일일 AI 한도 초과·AI 오류 시: ③을 건너뛰고 ④로 — **위젯은 계속 동작**한다.

## 4. 데이터 설계

### 4.1 content.ts 스키마 (Phase A, Phase C에서 DB 테이블과 1:1)

```ts
type ChatNode   = { id: string; message: string; buttons: ChatButton[] }
type ChatButton = { label: string; goTo?: string; action?: ActionRef }   // goTo=노드전이, action=카드
type ChatFaq    = { id: string; questions: string[]; answer: string; category: string; followUp?: string[] }
type ChatAction = { id: string; type: "tel"|"link"|"kakao"|"walla"; label: string; value: string }
type ChatPolicy = { id: string; keywords: string[]; answer: string; actions: string[] }  // 하드차단
```

초기 콘텐츠 출처: 시나리오 문구·버튼 구성은 인수인계 문서 2·4장, FAQ 44건은
`faq_upload_template_ko-260105-.xlsx` (**수령 대기 — P0**). 수령 전에는 문서 4.1 표 + FaqSection.tsx의
5문항으로 골격을 만들어 배선 검증까지 완료해 둔다.

### 4.2 Supabase 마이그레이션 (Phase A: 로그만)

```sql
-- 20260820000000_chatbot_logs.sql
create table chatbot_logs (
  id bigint generated always as identity primary key,
  session_id text not null,            -- sessionStorage 익명 ID (개인식별 불가)
  kind text not null check (kind in ('button','faq_hit','policy_block','ai_answer','fallback')),
  user_input text,                     -- 마스킹 후 저장 (전화번호·주민번호 패턴 제거)
  node_or_faq_id text,
  source_doc_ids text[],               -- Phase B: AI 근거 문서
  created_at timestamptz not null default now()
);
alter table chatbot_logs enable row level security;   -- 정책 없음 = service_role 전용
create table chatbot_usage (
  day date primary key,
  ai_calls int not null default 0
);
alter table chatbot_usage enable row level security;
```

보관: 90일 경과 로그 자동 삭제(pg_cron 또는 keepalive cron 확장). 개인정보처리방침에 챗봇 로그 항목 추가.

| # | 작업 |
|---|---|

### Phase D — 전환(cutover)

1. 채널톡 콘솔에서 **상담 이력 export** (전환 후 복구 불가)
2. prod Supabase에 마이그레이션 적용 → `NEXT_PUBLIC_CHATBOT_ENABLED=true` (Production)
3. 같은 배포에서 채널톡 스니펫 제거 (`app/layout.tsx:80-93`) + `app/admin/layout.tsx`의 ChannelIO 로직 제거
   — 위젯 2개가 동시에 뜨는 기간을 만들지 않는다
4. 1~2주 모니터링 (fallback률·AI 비용·로그) 후 채널톡 구독 해지
5. 롤백 경로: flag off + 스니펫 복원 커밋 revert
