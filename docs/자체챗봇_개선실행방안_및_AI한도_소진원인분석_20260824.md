## 1. 결론

### 1.1 500회는 agent QA가 소진했는가?

**그렇다. 사용자 트래픽이 아니라 agent의 자동 QA·채널톡 재생·수정 확인 요청이 내부 한도를
소진한 것으로 판단할 충분한 직접 증거가 있다.**

한도 도달 전 DB 로그에서 내부 예산을 소비한 것으로 역산되는 요청은 498건이다.

| 소비 주체 | 전체 로그 | 예산 소비 요청 | 500회 대비 | 근거 |
|---|---:|---:|---:|---|
| `qa-*` 자동 QA | 400 | **317** | 63.4% | `scripts/qa-run.mts`가 매 요청에 `qa-<random>` 세션 사용 |
| `ct_replay_*` 채널톡 재생 | 196 | **168** | 33.6% | `scripts/ct-replay.mts`의 고정 세션 접두사 |
| 수정 확인용 agent probe | 17 | **13** | 2.6% | `warm`, `fix2_*`, `fix3_*`, `fix4_*`, `nc_*`, `ctx_probe` |
| 사람 브라우저 `s_*` | 4 | **0** | 0% | 버튼·FAQ만 사용, AI 예산 경로 없음 |
| 사용량 행과 로그 차이 | - | **2** | 0.4% | 소비 이벤트 감사 로그가 없어 직접 RPC인지 로그 유실인지 확정 불가 |
| 합계 | - | **500** | 100% | 기록으로 특정된 agent 요청만 498건 |

자동 QA와 replay만 485/500, 즉 97.0%다. 수정 확인 probe까지 포함하면 498/500, 즉 99.6%다.
나머지 2회가 무엇이든 agent 실행이 없었다면 한도에 도달하지 않았다는 인과관계는 변하지 않는다.

최초 `daily_limit`은 사용자 질문보다 먼저 발생했다.

| 시각(KST) | 세션 | 질문 | 결과 |
|---|---|---|---|
| 13:28:40 | `qa-2t75z62o33f` | 병원 와이파이 비밀번호 | `daily_limit` |
| 13:28:43 | `qa-lknyd5cm8k` | 작년 환자 수 | `daily_limit` |
| 13:28:46 | `qa-730eaue99bn` | 의사 선생님 실력 | `daily_limit` |
| 14:14:17 | 사용자 `s_mt6s6h8s_ejgos2np` | 지원되는 교통 서비스 | `daily_limit` |

agent QA가 이미 13:28에 한도 소진을 확인했는데도 사용량을 복구하거나 사람 QA 서버를 분리하지
않았고, 약 45분 뒤 사용자가 같은 고갈 상태를 만났다.

### 1.2 결제했는데 왜 차단됐는가?

Google 결제 한도와 애플리케이션 내부 한도는 서로 다른 장치다.

```text
애플리케이션 내부 예산
CHATBOT_DAILY_AI_LIMIT → Supabase consume_chatbot_budget() → 먼저 차단

Google API 결제·quota
generateText() → 내부 예산을 통과한 뒤에만 도달
```

사건 당시 `CHATBOT_DAILY_AI_LIMIT=500`이므로 결제 여부와 무관하게 501번째 AI 경로 요청부터
코드가 차단했다. 로그의 `daily_limit`은 제공자 결제 한도가 아니라 이 내부 차단을 뜻한다.

기존 출시 검토 문서에는 이를 “Gemini FreeTier 500회 소진”으로 판단한 기록도 있다. 그러나
2026-08-24 사용자 실패 네 건의 직접 증거는 모두 애플리케이션의 `daily_limit`이며, 이 분기는
`generateText()`보다 먼저 실행된다. 따라서 해당 사용자 장애를 Google 제공자 quota로 설명한 것은
근거가 잘못 연결된 진단이다. 8월 23일에 별도의 제공자 quota 오류가 있었는지는 원문 오류 응답을
보존하지 않아 지금 확정할 수 없다.

### 1.3 현재도 한도 문제인가?

현재는 소진 상태가 아니다.

| 환경 | 내부 한도 | 현재 사용 | 실제 호출 결과 |
|---|---:|---:|---|
| 로컬 | 2,000 | 158 | `source=ai`, `provider=google-direct`, 정상 응답 |
| 최신 Preview | 500 | 6 | 최근 2회 중 `model_refused` 1회, 다음 호출은 `source=ai`, `provider=google-direct` |
| Production | 자체 API 없음 | 해당 없음 | 채널톡 사용 중, 자체 API 404 |

로컬 `.env.local`만 2,000으로 바뀌었고 Preview는 여전히 500이다. Preview 한도를 바꾸려면 Vercel
환경변수 변경 후 새 배포가 필요하며, 새 응답의 `usage.limit`가 변경값인지 확인해야 한다.

### 2.2 실제 API 검증

한도 상향 후 로컬에서 사용자 질문을 반복 호출했고 `used=152~158`, `limit=2000`으로 모두 AI 경로를

`used=6`, `limit=500`, `provider=google-direct`로 정상 답했다. 정상 답변에는 방문·신청서·카카오톡·
전화, 3일 전 권장, 환자 정보와 예약일이 포함됐다.

따라서 **한도 상향은 `daily_limit`으로 즉시 차단되던 가용성 문제를 해소한다.** Preview의 한도는
아직 상향하지 않았지만 현재 6/500이어서 소진 상태가 아니며 Google 직접 호출도 성공했다. 다만
직전 1회가 `model_refused`였으므로 다음은 해결되지 않았다.

- 답변에 필요한 사실이 빠지는 문제
- 질문 표현에 따른 FAQ 오분류
- 문자 기반 검색 실패
- LLM 비결정성
- 전체 KB 22,000여 토큰 입력 비용
- QA와 사람 사용량의 공유
- DB 장애를 `daily_limit`으로 잘못 표시하는 문제

### 2.3 현재 한도 구현의 추가 결함

1. **QA·사람·agent probe가 같은 namespace를 사용한다.**
   로컬은 모두 `development`로 기록된다. 한도를 2,000으로 올려도 같은 사고가 늦게 재발한다.

2. **DB 장애도 `daily_limit`으로 표시된다.**
   DB 설정 누락 또는 RPC 오류 시 `consumeDailyBudget()`은 `ok=false`를 반환하고 API는 이유를 구분하지
   않고 `fallback("daily_limit")`을 사용한다. 앞으로 `daily_limit` 로그만으로 실제 소진을 단정할 수 없다.

3. **카운터 날짜가 UTC 기준이다.**
   `new Date().toISOString().slice(0, 10)`을 사용하므로 KST 기준 오전 9시에 날짜가 바뀐다. 병원 운영
   일일 지표와 자정 기준을 기대하면 어긋난다.

4. **한 요청과 실제 모델 호출 수가 다르다.**
   예산은 API 요청당 한 번 차감하지만 출처가 빠지면 `generateText()`를 한 번 더 호출한다. 따라서
   내부 카운터 500은 실제 모델 요청 500회를 보장하지 않으며 비용 방어 지표로도 불완전하다.

5. **현재 사용량 행의 변경 감사 기록이 없다.**
   사건 당시 500이던 로컬 사용량 행은 이후 낮아졌지만 언제 누가 초기화했는지 확인할 테이블이나
   로그가 없다. 이 때문에 500 중 2회의 출처를 확정하지 못했다.

6. **환경별 설정이 드리프트했다.**
   로컬 2,000, Preview 500이며 Production에는 자체 API가 없다. 설정 표와 배포 검증이 없으면 개발자가
   보고 있는 결과와 검수자가 보는 결과가 달라진다.

## 3. 한도 수정 후에도 재현되는 응답 품질 문제

한도를 올린 뒤 정상 AI 응답이 나온다는 사실과 채널톡 수준으로 정확하다는 사실은 다르다.

### 3.1 교통·이동 서비스 질문 3회 반복

질문: `지원되는 교통 서비스는 무엇이 있는가?`

채널톡 최신 답변 기준 핵심 요소는 검사실·진료실 이동, 보행 부축, 휠체어/이동식 침대,
1:1 길 안내, 병원 내부 약국 동행, 병원 내부 한정이다.

| 필수 요소 | 자체 챗봇 3회 포함 횟수 | 판정 |
|---|---:|---|
| 검사실·진료실 이동 | 1/3 | 불안정 |
| 명시적 보행 부축 | 0/3 | 누락 |
| 휠체어/이동식 침대 | 3/3 | 안정 |
| 1:1 길 안내 | 0/3 | 누락 |
| 병원 내부 약국 동행 | 1/3 | 불안정 |
| 병원 내부 한정 | 3/3 | 안정 |

첫 두 답변은 “외부 약국까지는 어렵다”는 문장을 포함했지만 “병원 내부 약국까지 동행”을 안내하지
않았다. 단순 `약국` 키워드 존재 여부로 평가하면 이를 통과시키는 거짓 양성이 생긴다.

세 번 모두 AI 성공이며 문서도 인용했지만 답변 완전성은 크게 달랐다. 현재 채점기의 “기대 문서 중
하나 인용” 방식으로는 이런 누락을 잡지 못한다.

| P1 | migration 주석은 embedding 컬럼을 말하지만 실제 DB에는 컬럼 없음 | 설계와 스키마 불일치 |
| P1 | FAQ의 일반 문장 부분 포함 0.9 | 구체적 서비스 질문 가로채기 |
| P1 | 브라우저 15초, QA/replay 90초·재시도 | API QA 성공과 실제 UX 불일치 |
| P1 | ChatWidget이 서버 FAQ를 `fallback` source로 저장 | 실제 브라우저 history와 replay history 불일치 |
| P1 | DB 오류와 실제 한도 소진을 동일 처리 | 운영 진단 불가 |
| P1 | 로그가 이름·생년월일·건강정보를 충분히 마스킹하지 못할 수 있음 | 개인정보 위험 |
| P2 | KB 직답 시 긴 원문 문서 전체 반환 | 상담형 응답 품질 저하 |
| P2 | in-memory 분당 제한은 Vercel 인스턴스별 | 전역 남용 방어가 아님 |
| P2 | `next.config.mjs`의 `ignoreBuildErrors=true` | 타입 오류가 배포 빌드에서 숨을 수 있음 |
| 별도 P0 | 운영 `main` 관리자 쓰기 API 미인증 | 챗봇 외 운영 보안 차단사항 |
| 별도 P0 | 로컬 Claude 설정의 평문 GitHub PAT | 즉시 폐기·재발급 필요 |

## 5. 권장 개선 순서

한도를 무제한으로 올리는 것부터 하면 원인이 숨고 QA 비용만 커진다. 다음 순서가 가장 작고 안전하다.

### 단계 A — 예산 격리와 진단 정상화(P0)

대상: `lib/chatbot/ratelimit.ts`, `app/api/chatbot/ask/route.ts`, QA 실행 설정, DB migration

1. 서버 환경변수 `CHATBOT_USAGE_NAMESPACE`를 추가한다.
   - 사람 로컬 QA: `manual-local`
   - 자동 QA: 실행별 `qa-<run-id>`
   - 채널톡 재생: `replay-<run-id>`
   - Preview: `preview`
   - Production: `production`
2. 자동 QA는 별도 포트의 서버 프로세스에서 실행해 namespace와 한도를 분리한다.
3. QA 시작 전 예상 AI 요청 수와 남은 예산을 검사하고 부족하면 실행 전 중단한다.
4. `consumeDailyBudget` 반환을 `allowed`, `exhausted`, `db_unavailable`, `db_error`로 구분한다.
5. KST 날짜 키를 명시적으로 계산한다.
6. 요청 수와 실제 `generateText()` 시도 수·토큰을 별도로 기록한다.
7. 사용량 초기화·수정은 actor/reason/시각이 남도록 감사 이벤트를 기록한다.
8. 환경변수 변경 후 새 배포에서 응답의 `usage.limit`를 확인하는 smoke를 필수화한다.

권장 한도는 임의의 500/2,000이 아니라 다음으로 정한다.

```text
사람 환경 한도 = 관측된 실제 일 최대 AI 질문 × 안전계수 + 장애 대응 여유
QA 환경 한도   = 평가 세트의 예상 AI 경로 수 × 허용 실행 횟수 + 재시도 여유
```

현재 실제 사용자 전체 상태 export와 일별 peak가 없으므로 Production 한도를 확정할 데이터가 없다.
결제 연결은 무제한 설정의 근거가 아니다.

### 단계 B — 핵심 업무 답변을 LLM 장애와 분리(P0)

신청 방법, 전화번호, 운영시간, 위치, 비용, 이동 지원 범위처럼 반드시 답해야 하는 항목은 승인된
짧은 답변으로 결정적으로 제공한다.

1. `short_answer`와 `required_facts`를 공식 콘텐츠로 관리한다.
2. “검사실 이동 + 신청”처럼 서비스 주제와 신청 의도를 함께 해석해 서비스 설명과 공통 신청 절차를
   조합한다.
3. `어떻게 신청하나요?` 같은 일반 FAQ는 입력 전체가 사실상 같은 문장일 때만 강한 부분 일치를 준다.
4. 현재 KB에 없는 “담당 매니저 상담 후 최종 결정”은 채널톡에서 무작정 복사하지 말고 병원 확인 후
   공식 KB에 추가한다.
5. LLM·DB 일부 장애 시에도 핵심 연락처·신청 방법은 제공되도록 한다.

### 단계 C — 실제 의미 기반 retrieval 도입(P1)

현재 migration 주석과 달리 DB에는 embedding 컬럼도 vector index도 없다.

최소 구현은 다음으로 제한한다.

1. 문서를 답변 단위의 짧은 chunk로 나눈다.
2. 임베딩과 기존 키워드 점수를 결합한 hybrid Top-K(예: 5)를 만든다.
3. 별도 reranker는 holdout 평가에서 필요성이 확인될 때만 추가한다.
4. LLM에는 59문서 전체가 아니라 Top-K 근거만 전달한다.
5. 낮은 검색 확신도에서는 추측하지 않고 담당자 연결로 보낸다.

이렇게 해야 `교통→이동`, `가정간호 신청`, 어순 변화가 개별 프롬프트 예시 없이도 일반화되고,
요청당 22,000여 input token 의존도도 줄어든다.

### 단계 D — QA 구조 재설계(P0/P1)

테스트를 비용과 목적별로 나눈다.

1. **무료·결정적 테스트**
   - 정책·FAQ 라우팅
   - 검색 Top-K
   - 필수 답변 템플릿
   - 한도 경계 DB 함수
2. **소규모 live canary**
   - 핵심 질문 10~20개
   - 모델·인증·timeout·인용 확인
3. **전체 live QA**
   - 커밋당 승인된 1회만 실행
   - 별도 namespace와 결과 파일 사용
4. **ChannelTalk 비교**
   - `closed`와 `initial` 등 모든 상태·페이지 수집
   - 튜닝 세트와 holdout 세트 분리
   - 답변 순서를 가린 독립 사람 채점

각 질문은 문서 번호가 아니라 다음 rubric으로 채점한다.

- 반드시 포함할 사실
- 포함하면 안 되는 사실
- 부정문과 긍정문의 방향
- URL·전화번호 정확성
- 지원 범위 제한
- 답변 시간 15초 이하
- 실제 브라우저에서의 표시·history 유지

현재 `tests/qa-result.json`의 100자 answer 절단을 제거하고 전체 답변, 커밋, 모델, 환경, namespace,
시각, 데이터 버전을 저장한다. `qa-set` 수와 result 수가 다르면 실행을 실패시킨다.

### 단계 E — 브라우저·관측·개인정보 마감(P1)

1. ChatWidget이 서버 `faq`, `policy`, `fallback` source를 보존하도록 수정한다.
2. QA도 실제 UI와 같은 15초 조건으로 별도 실행한다.
3. 운영 지표에 namespace별 사용량, 남은 예산, 모델 시도 수, token, fallback reason, p95 지연을 표시한다.
4. 이름·생년월일·건강정보 로그 정책과 90일 보존을 병원과 승인한다.
5. 교차 브라우저·실기기·스크린리더 검수를 완료한다.

## 7. 권장 실행 단위

| 작업 단위 | 목적 | 완료 증거 |
|---|---|---|
| 1. 예산 namespace·오류 구분 | 사람 서비스와 agent QA 격리 | 같은 QA 후 manual 사용량 불변 |
| 2. QA preflight·실행 메타 | 반복 실행과 stale 결과 차단 | commit/env/model/count 일치 |
| 3. FAQ 일반 부분 포함 수정 | 가정간호 오분류 제거 | 어순 변형 회귀 통과 |
| 4. 핵심 답변 required facts | 신청 필수정보 누락 제거 | 5회 반복 전 항목 포함 |
| 5. hybrid Top-K | 의미 검색과 비용 개선 | 독립 holdout + input token 감소 |
| 6. 실제 UI·ChannelTalk 재평가 | 대체 가능성 판단 | 독립 승인, P0/P1 0건 |

한 번에 전체 구조를 교체하지 않는다. 1~2번으로 재발 가능한 서비스 중단과 잘못된 QA를 먼저 막고,
3~4번으로 현재 확인된 오답을 결정적으로 해결한 뒤, 5번의 의미 검색은 독립 holdout으로 효과를
증명하면서 적용한다.

## 최종 판단

500회 소진은 실제 사용자가 많아서가 아니라 agent가 live QA와 replay를 같은 `development` 예산으로
반복 실행한 결과다. 결제 연결은 이 내부 한도를 해제하지 않는다. 로컬 한도 2,000 변경 후 API
가용성은 회복됐지만, 답변 필수정보 누락·FAQ 오분류·의미 검색 부재·잘못된 QA 판정은 그대로다.

따라서 올바른 다음 조치는 “한도를 더 올린다”가 아니라 **agent QA 예산 격리 → 한도·DB 오류 진단
분리 → 핵심 업무 결정적 답변 → 의미 기반 Top-K → 독립 전체 답변 평가** 순서다.
